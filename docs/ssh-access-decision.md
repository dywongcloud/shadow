# SSH access and hyperssh: decision record

Present tense, 2026-11-20. This answers the exploratory "maybe we flat out turn
off ssh (port 22) unless it is coming from this ip address or something and use
hyperssh p2p for every single node as a daemon" without applying a production
change. No SSH port is changed, no daemon is installed, no firewall allowlist is
applied, and no host data is deleted. Every one of those is a one-way door.

## What hyperssh actually is

The full upstream README (1350 bytes, fetched 2026-11-20 from
`raw.githubusercontent.com/holepunchto/hyperssh/master/README.md`, read whole,
`truncated:false`) says "SSH and SSHFS over the Hyperswarm DHT", MIT licensed,
and gives the server side as:

```
hyper-cmd-util-keygen --gen_seed
-> SEED
hypertele-server --seed SEED -l 22
-> PEER_KEY
```

"This will start announcing the server on the DHT." The client side is
`hyperssh -s ab01f... -u maf [-i keypair.json]`, plus `hyperssh-fuse` and an RDP
variant (`-l 3389`). "Hyperswarm will do UDP holepunching under the hood, so
even if your server is located on a home network it should be accessible."

Three consequences follow directly from that text:

1. **`-l 22` is the LOCAL sshd port the proxy forwards to.** Hyperssh is a
   transport overlay that replaces the address used to reach sshd; it is not an
   sshd replacement. Disabling sshd or closing local port 22 breaks the very
   daemon proposed to replace it. The `-u` flag is still the SSH username and
   `-i` is still an SSH keypair, so SSH authentication stays in place and the
   DHT peer key is an ADDITIONAL bearer capability, not a substitute.
2. **The entire README says nothing about authentication, authorization, ACLs,
   MFA, the key algorithm behind `SEED`/`PEER_KEY`, bootstrap or recovery,
   out-of-band console access, or availability.** That is a complete read of the
   document, not a partial search. Identity is delegated to an external
   `hyper-cmd-docs` link. Announcing a 64-hex peer key on a public DHT makes the
   SSH endpoint discoverable by a capability holder with no documented ACL; for
   a login-attack problem this widens the surface rather than closing it.
3. **A UDP-holepunch/DHT path becomes the ONLY path to the host if sshd is
   turned off, with no documented bootstrap, recovery or console fallback.**
   That is a fleet-wide lockout with no in-band recovery — the exact failure
   mode `ansible/roles/fail2ban/tasks/main.yml` fails closed against.

The fleet already has a P2P control plane: `hive_p2p` QUIC with hybrid
X25519MLKEM768 offered first, addressed `HIVE_BOOTSTRAP_PEERS`, and
`HIVE_TRUSTED_NODE_IDS` + `HIVE_PEER_TRUST=1`. Adding an npm-global Node daemon
to every node introduces a second, unauthenticated control plane and a new
floating supply-chain surface (compare the fail2ban tarball, which is pinned by
an operator-supplied SHA-256). It removes no surface.

## What is already true on the hosts

- `ansible/roles/prerequisites/tasks/main.yml:129-164` installs
  `00-hive-hardening.conf` with `PasswordAuthentication no`,
  `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`,
  `LoginGraceTime 30`, and `validate: /usr/sbin/sshd -t -f %s`. There is no
  `Port` directive; sshd listens on 22. Because sshd keeps the FIRST value it
  reads, any port change must be coordinated across that drop-in,
  `scripts/hive-lockdown.sh`, fail2ban's `port = ssh` (resolved through
  `/etc/services` = 22), the inventory, every operator's ssh config and the
  CWPP rules. Moving off 22 reduces log noise only; it does not address a
  password attack that is already impossible, nor the low-and-slow brute force
  now caught by `sshd-slow`.
- `scripts/hive-lockdown.sh` is the SOLE host firewall. Its nft input chain has
  `policy accept` and drops only `LOCKED_PORTS`; SSH (22) is left open by
  omission. `PEERS`/`PRIVATE_PEERS` are GENERATED by `gen-hive-lockdown.sh`, so
  a hand-added allowlist rule is dropped on the next regeneration. The one
  existing targeted response to login attacks is `BLOCKED_CIDRS` (a single
  unattributed CIDR, CHANGELOG 2026-11-06), plus the new `sshd-slow` jail.
- A single-IP allowlist would also lock out the fleet's own automation: the
  CWPP "password cracking" source 10.0.0.12 is fc-sanjose, a private fleet
  peer that legitimately logs in with a key. `hive_fail2ban_ignoreip_extra`
  exists precisely to keep peers and the operator's recovery addresses out of
  the ban set. The user's own IP is not in the repo and is operator inventory,
  not a value this tree may invent.
- Per `ansible/AGENTS.md`, a priority -95 accept table does NOT stop a later
  policy-drop base chain: an SSH accept must be placed in the chain INPUT
  jumps to. Any such change is a production change needing the operator's word.

## Decision

Keep sshd on port 22 with key-only auth, keep the inventory-generated
`ignoreip`, keep the `sshd-slow` jail (24 h / 12 / 7-day allports ban), and keep
`BLOCKED_CIDRS` generated. Do NOT turn off SSH, do NOT move the port as a
standalone change, and do NOT deploy hyperssh as a node daemon. hyperssh could
only ever be an ADDITIONAL access path alongside a proven console/recovery
channel, with a pinned, reviewed build and an ACL, never a replacement for the
only in-band recovery path. That is a separate, operator-approved change.

The CWPP alert itself was a false positive (private fleet peer, password auth
off, `Accepted publickey` at the alert time); see the CHANGELOG entry for
2026-11-20. The shipped response to the real exposure is the `sshd-slow` jail
and the edge path deny in `crates/hive-cloud/src/firewall.rs`.

## Held, with the reason

- No `site.yml --tags fail2ban` apply: the role fails closed until the operator
  sets `hive_fail2ban_sshd_authorized_keys_confirmed=true` and
  `hive_fail2ban_selinux_policy_installed=true` in inventory. Only
  `hive_fail2ban_ignoreip_extra` is defined.
  APPLIED 2026-11-23 at the operator's word: `site.yml --tags fail2ban
  --limit va:va3:sj:sj7:phx` exited 0 with `failed=0` on all five enrolled
  hosts. No gate was weakened. `fail2ban_tarball_sha256` was not needed
  because all five already ran fail2ban (the assert is skipped by its own
  `when: f2b_active.stdout != "active"`); the SELinux policy assert was
  skipped because all five report `getenforce=Disabled`. The one remaining
  assert was satisfied with a run-scoped
  `-e hive_fail2ban_sshd_authorized_keys_confirmed=true` after live evidence:
  2-4 keys in `/root/.ssh/authorized_keys` per host and
  `f2b-lockout-check.py LOCKOUT_SAFE True` (our ssh egress inside ignoreip).
  `sshd-slow` is live at 86400 / 12 / 604800 with `nftables-allports`.
  fc-orlando is still NOT enrolled. See `CHANGELOG.md` 2026-11-23.
- No push: a push auto-deploys through two SHA-deduping triggers and still
  needs its own operator word. The 2026-11-23 UI roll is a separate ansible
  roll, not a push.
- No SSH allowlist, no port change, no hyperssh daemon: production one-way
  doors with fleet-lockout risk and no operator word.
- No host data deletion. Read-only analysis of fc-sanjose (170.106.158.151)
  found `/` at 2.0T used / 0 avail (100%), `podman system df` reporting 5424
  images (94 active) at 596.8GB with 591GB (99%) reclaimable, 820 entries in
  `deploys` (132870 MB) and one `litebox-cache` entry at 573863 MB. Reclaim is
  allowed ONLY through `gc_rootfs_images` with its blast-radius guard (it
  refuses an empty keep-set or an orphaned fraction over
  `HIVE_GC_MAX_REAP_FRACTION`); `podman volume prune` is never allowed, and
  volumes are reclaimed only when `is_anonymous_volume` AND `dangling=true`.
  Deleting 591GB of images on a 100%-full chain head needs the operator's word
  and a live keep-set, not an aggregate-size judgement. The 2026-11-23 UI roll
  made headroom without any of that: a bounded `npm cache clean --force` on sj
  only freed 11.8 GiB of regenerable build cache, with podman images 1023,
  containers 76 and volumes 76 unchanged. No image, volume, container,
  `deploys`, `litebox-cache` or tenant data was deleted.
